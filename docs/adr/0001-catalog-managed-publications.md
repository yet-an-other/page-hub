# Catalog-managed Publications

Page Hub's private catalog, not the presence of an object or prefix in storage, defines a managed Publication. Projects and Publications have stable identities independent of their paths. Each Publication points to an immutable accepted manifest revision that records its exact object keys, serving metadata, entry point, and routing mode. Reconciliation records observed storage state separately, so out-of-band writes cannot silently become accepted state. We chose this model over prefix inference and public object metadata because Page Hub is the mutation authority and must preserve private descriptions, history, ownership, and existing URLs.

The catalog also keeps Adoption candidates, private display names and descriptions, operation records, and deletion tombstones. One object can belong to only one Publication, and active route scopes cannot overlap. Adoption creates catalog records without changing stored objects; each existing top-level prefix becomes a Project with one root Publication and may retain a legacy compatibility profile. Management writes fail closed when the catalog is unavailable, so its deployment must include backup and restore. The [legacy adoption and publishing cutover](../legacy-adoption-and-publishing-cutover.md) contract defines the initial batch, reconciliation, emergency access, and revocation of the old direct writer.
