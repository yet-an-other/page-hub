# Run the private manager on s3-node behind the existing authentication gateway

Page Hub will be one Go binary with embedded manager assets and a local SQLite catalog. The first deployment runs one instance as an unprivileged, resource-limited systemd service on `s3-node`, reached by nginx through a protected Unix socket. nginx continues to serve public Publication requests directly from RadosGW, so Page Hub downtime does not interrupt existing public reads. The manager has no high-availability requirement.

nginx reserves `/` and `/_page-hub/` for Page Hub and rejects `_page-hub` as a Project path. oauth2-proxy owns the OIDC flow and a 24-hour secure, HTTP-only, SameSite=Lax session against the existing internal ZITADEL service. Its exact-email allowlist admits the operator. nginx strips client identity and authorization headers, authenticates every manager request, and supplies an opaque assertion that Page Hub checks. Sign-in requires LAN or VPN access, but an established session may use the public origin. Manager documents redirect unauthenticated requests to sign-in, APIs return JSON `401`, and authentication or manager outages return `503` without entering Publication fallback. Public Publication routes do not authenticate and strip manager cookies and credentials before proxying to RadosGW.

The SQLite catalog uses transactions, foreign keys, migrations, and serialized management writes. Deployment takes and verifies a pre-migration backup before stopping the service and applying forward migrations. Nightly online backups write a current snapshot and 30 days of timestamped snapshots to a private, prefix-scoped AWS S3 location with provider-managed encryption. Backups and restores must pass `PRAGMA quick_check`; rollback across an incompatible migration requires an explicit restore followed by storage reconciliation. Private descriptions may contain management notes but not credentials or other secrets.

The public Page Hub repository defines the portable application and deployment contracts. The private homelab repository owns the concrete nginx, oauth2-proxy, systemd, secret injection, backup, monitoring, and recovery configuration. It installs a pinned, checksummed binary release and supplies root-owned secret files. Local health checks, structured journald logs, ntfy backup-failure alerts, and post-deploy authentication and Publication smoke tests cover the deployment without exposing private catalog or session data.
